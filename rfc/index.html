1.  Introduction

   The author is a hobbyist developer.  An interest in cybersecurity
   drove a desire to understand what programs actually do under the
   hood.  That question led deeper: debugging led to disassembly,
   disassembly led to PE headers and instructions, and instructions led
   to memory layouts, data and file formats, and eventually to the
   computational machinery and electrical currents beneath the
   interfaces used every day.

   The author learns by building.  Sometimes that is a conventional
   application; more often it is a tool built to understand a technology
   or eliminate a repetitive task.  Whenever the author picks up a new
   language, his ritual is to implement DES by hand, bit by bit and
   table by table.  By the time a cipher encrypts correctly, the
   language's rough edges have been mapped.

   The author is not a senior engineer and does not pretend to be one on
   the Internet.  These projects are the working notes of a developing
   programmer, presented as honestly as possible -- including what is
   unfinished.

2.1.  JournalSec

   Title:      JournalSec - encrypted local journal
   Kind:       local app
   Status:     prototype [unaudited]
   Stack:      Express, AES-256-GCM, Argon2id
   Topics:     cryptography; password-based key derivation; protected
               data; practical security implementation
   Summary:    A locally oriented journal with encrypted storage: keys
               derived from a passphrase, entries sealed with
               authenticated encryption.
   Problem:    A journal is the most personal data there is, and "it's
               just on my machine" is not a security model.  The goal
               was to practice best security practices rather than ship
               a product.
   Approach:   Passphrases are stretched with Argon2id into an envelope-
               wrapped encryption key; entries are sealed with
               AES-256-GCM so confidentiality and integrity are both
               covered.  Everything runs locally on a small Express
               service; the attack surface is the point of this project.
   Note:       Prototype.  It has not had an independent security audit
               and should not be trusted with data you cannot afford to
               lose.  The crypto primitives are standard; the
               surrounding code is hobbyist quality.
   Source:     private until it deserves to be public

2.2.  UBE

   Title:      UBE - Universal Beatmap Extractor
   Kind:       format tooling
   Status:     active development
   Stack:      JavaScript, Node

   Topics:     file-format parsing; data modelling; format
               interoperability; archive extraction; audio/image assets
   Summary:    A beatmap converter for mania rhythm games: parse
               multiple formats into one shared internal representation,
               convert between them.
   Problem:    Every rhythm game speaks its own beatmap dialect.  Charts
               people care about are locked inside format-specific
               silos, and existing converters tend to cover one narrow
               pairing at a time.
   Approach:   Each supported format gets a parser that maps onto a
               single intermediate representation: timing, lanes, notes,
               and metadata as plain data.  Converters are just
               parser/serializer pairs, which makes adding a new format
               a matter of writing one side of the mapping.  Assets
               (audio, images) are pulled from the game-specific archive
               or format during extraction.
   Note:       osu! parsing is the furthest along.  Quaver, StepMania
               and beatmania are targeted formats, not finished ones;
               treat support as partial until the parser tables say
               otherwise.  Beatmap editing is future work, not a shipped
               feature.
   Source:     private until it deserves to be public

2.3.  Dekiru

   Title:      Dekiru - Japanese sentence learning tool
   Kind:       web app
   Status:     active development
   Stack:      Next.js, SQLite, Python, SudachiPy
   Topics:     NLP / morphological analysis; language learning; data
               pipelines; SQLite full-text search; Japanese linguistics
   Summary:    A Japanese reading tool built around real Tatoeba
               sentences: tap any word to see its meaning, readings, and
               full conjugation table with the current inflection
               highlighted.
   Problem:    Vocabulary apps teach words in isolation.  Reading real
               Japanese means encountering words mid-conjugation, inside
               polite constructions, stacked with auxiliary verbs; none
               of which maps cleanly onto a dictionary entry.  Most
               tools either skip that gap or paper over it with
               furigana.
   Approach:   A Python pipeline parses JMdict, KANJIDIC2, and Tatoeba
               into SQLite, then runs SudachiPy over every sentence to
               tokenize and resolve each morpheme to its dictionary
               entry.  A grouping pass merges auxiliary chains into
               learner-facing display units (one clickable chunk, not
               four).  The Next.js frontend renders tappable sentence
               tiles; tapping one opens a word card showing the head
               word's conjugation table with the active inflection row
               highlighted, followed by a morpheme breakdown of each
               piece (honorific prefix, verb stem, auxiliary) as its own

2.4.  DES, by hand

   Title:      DES, by hand - from-scratch DES in every language I learn
   Kind:       learning exercise
   Status:     ongoing - multi-language
   Stack:      Python, JavaScript, C++ (planned), C# (planned)
   Topics:     block ciphers; Feistel networks; bit manipulation;
               S-Boxes; key schedules; cli tools
   Summary:    A recurring ritual: implement DES from nothing in each
               new language picked up; no crypto libraries, just loops,
               literal tables, and bit-by-bit string surgery.
   Problem:    Tutorials teach syntax; they do not teach how a language
               feels under real work.  The author wanted one fixed, non-
               trivial problem with enough structure (real logic, real
               bit manipulation, real edge cases) to force a pass
               through a language's loops, strings, types, and idioms.
   Approach:   The specification is followed literally and awkwardly on
               purpose: initial permutation, expansion, S-Box lookups,
               P-Box, and the key schedule are all declared as plain
               table arrays.  Bits are handled by indexing strings; if
               the character at position n is `0` do this, if it is `1`
               do that.  Only loops, functions, and the occasional
               class; native API calls are kept to a minimum.  A small
               CLI takes a hex or plaintext key plus a mode and outputs
               the encrypted result in hex.  The constraint is the
               point; by the time DES encrypts and decrypts correctly,
               the language's rough edges are mapped.
   Note:       Python and JavaScript versions work end to end.  C++ and
               C# are planned, with more languages after; each
               implementation lives in its own folder of one repository,
               and the collection itself is the project.
   Source:     private until it deserves to be public

2.6.  OffRed

   Title:      OffRed - local SubReddit archiver
   Kind:       desktop app
   Status:     working prototype
   Stack:      Electron, SQLite
   Topics:     desktop software; local persistence; data retrieval; web
               tech on a desktop runtime
   Summary:    An Electron application for archiving Reddit content
               locally, stored in a real database you own.
   Problem:    Content posted to platforms disappears: deleted, removed,
               privatized.  Archiving it means pulling it out of the
               platform context and keeping it somewhere durable and
               queryable.
   Approach:   Electron hosts a familiar web-technology UI while the
               data layer is a local SQLite database: retrieval,
               storage, and browsing all run on the machine, no server
               required.  The interesting part was the seam where web
               conventions meet a desktop runtime and a relational
               schema.
   Note:       A working prototype, not a polished product.  Core
               retrieval and storage work; the UI and edge cases are
               where the remaining effort sits.
   Source:     private until it deserves to be public

4.1.  Proficiency Tiers

   Each technology below is assigned exactly one of the following tiers,
   listed from strongest to weakest:

   primary:    Used regularly.  The author can build with it
               independently without constantly consulting
               documentation.

   proficient: The author can work with it comfortably and understands
               its common patterns and concepts, though it is not
               necessarily the strongest technology.

   knowledge:  The author has built meaningful things with it and
               understands the fundamentals, but has less experience
               with it than with the primary technologies.

   familiar:   Used in a project or course.  The author understands the
               basics, but would need to revisit the documentation
               before doing substantial work with it.

   exposure:   Encountered or experimented with, without enough
               practical experience to claim proficiency.
